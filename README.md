# Shakha — Custom Language Lexical Analyzer

A **Flex/Lex-based lexical analyzer** for a small, Bengali-inspired programming language called **Shakha**. It reads a source program from `input.txt`, recognizes language tokens, records their line numbers, and writes a categorized token report to `output.txt`.

> **Project scope:** This is a **lexer**, not a compiler or interpreter. It recognizes tokens but does not execute the program, validate complete grammar, or enforce operator precedence.

## Features

- Bengali-inspired, romanized keywords such as `dhoro`, `yadi`, `nahole`, `jotokkhon`, and `dekho`
- Token recognition for declarations, types, control flow, functions, operators, literals, identifiers, and delimiters
- `#` single-line comments and `/* ... */` multiline comments
- Unterminated multiline-comment reporting in the corrected `shakha_fixed.l`
- Line-numbered diagnostics and token statistics
- Reports unknown symbols (for example `@`)
- Accepts UTF-8 Bengali identifiers as byte sequences (not full Unicode identifier validation)

## Technology

- **Flex** — scanner generator
- **C** — lexer actions and output reporting
- **GCC** — compilation

## Project files

```text
Shakha/
├── shakha.l             # Main Lex source (if using original name)
├── shakha_fixed.l       # Corrected lexer source (optional replacement)
├── input.txt            # Shakha sample/source program
├── README.md
├── lex.yy.c             # Generated by Flex
├── ubs.exe              # Generated executable on Windows
└── output.txt           # Generated token report
```

Only the `.l` source and `input.txt` are needed before building. `lex.yy.c`, the executable, and `output.txt` are generated.

## Language reference

### Keywords and constructs

| Category | Shakha token | Meaning |
| --- | --- | --- |
| Declaration | `dhoro` | Variable declaration |
| Function | `def` | Function definition |
| Function | `ret` | Return statement |
| Output | `dekho` | Output function |
| Condition | `yadi` | If |
| Condition | `nahole_yadi` | Else if |
| Condition | `nahole` | Else |
| Loop | `jotokkhon` | While |
| Loop | `loop` | For-style loop |
| Boolean value | `satya` | True |
| Boolean value | `mithya` | False |

### Data types

| Token | Intended type |
| --- | --- |
| `sankhya` | Integer |
| `doshomik` | Floating-point |
| `lekha` | String |
| `jukti` | Boolean |
| `talika` | Array/list |

These words are recognized as **data-type tokens**. The lexer does not implement type checking or conversion.

### Library-function names

`sort`, `push_back`, `binary_search`, `replace`, `len`

These are recognized by the lexer; their runtime implementations are **not** provided by this project.

### Operators

| Class | Recognized tokens |
| --- | --- |
| Arithmetic | `+`, `-`, `*`, `/`, `%` |
| Relational | `<`, `>`, `<=`, `>=` |
| Equality | `==`, `!=` |
| Logical | `not`, `and`, `or` |
| Assignment | `=` |

### Operator precedence (proposed grammar specification)

Highest to lowest:

| Priority | Operator(s) | Associativity (proposed) |
| --- | --- | --- |
| 1 | `(` `)` grouping | N/A |
| 2 | `not` | Right-to-left |
| 3 | `*`, `/`, `%` | Left-to-right |
| 4 | `+`, `-` | Left-to-right |
| 5 | `<`, `>`, `<=`, `>=` | Non-associative (recommended) |
| 6 | `==`, `!=` | Non-associative (recommended) |
| 7 | `and` | Left-to-right |
| 8 | `or` | Left-to-right |
| 9 | `=` | Right-to-left |

**Note:** This is a suggested precedence model for a future parser. Flex recognizes tokens but **does not enforce** precedence or associativity. Unary minus is not separately defined in the lexer.

### Other syntax

| Token | Recognized purpose |
| --- | --- |
| `$` | Statement terminator |
| `:` | Block start marker |
| `;` | Block end marker |
| `(`, `)` | Parentheses |
| `[`, `]` | Brackets |
| `,` | Separator |
| `# ...` | Single-line comment |
| `/* ... */` | Multiline comment |

## Example input

Save this as `input.txt`:

```text
# Shakha demo

dhoro naam = "ullas"$
dhoro a = 10$
dhoro b = 5$
dhoro result = a + b * 2$

yadi (result >= 20 and a != b):
    dekho("Condition met")$
;

# Unknown symbol test
dhoro test = 5 @ 3$
```

This is **source text to tokenize**. It is not executed or evaluated by the lexer.

## Build and run

### Windows PowerShell (Flex + GCC)

From your project directory, for example `D:\code\compiler`:

```powershell
flex shakha.l
# Or use: flex shakha_fixed.l

gcc lex.yy.c -o ubs.exe
.\ubs.exe
Get-Content output.txt
```

PowerShell requires the `.\` prefix to execute a program from the current directory: use **`.\ubs.exe`**, not `ubs`.

### Ubuntu / Linux

```bash
sudo apt update
sudo apt install flex gcc
flex shakha.l
# Or use: flex shakha_fixed.l

gcc lex.yy.c -o ubs
./ubs
cat output.txt
```

The lexer opens `input.txt` and creates/overwrites `output.txt` in the **current working directory**. Make sure you run the executable from the folder containing `input.txt`.

## Example output (excerpt)

```text
COMMENT DETECTED - LINE 1
VARIABLE DECLARATION DETECTED - LINE 3
IDENTIFIER DETECTED: naam - LINE 3
ASSIGNMENT OPERATOR DETECTED - LINE 3
STRING LITERAL DETECTED - LINE 3
STATEMENT TERMINATOR DETECTED - LINE 3
```

For the final test statement, the report also includes:

```text
UNKNOWN SYMBOL '@' - LINE 14
```

The report ends with this summary structure (counts depend on the input):

```text
TOKEN SUMMARY
Keywords              : ...
Data Types            : ...
Operators             : ...
Control Statements    : ...
Functions             : ...
User Defined/IDs      : ...
Literals              : ...
Comments              : ...
Symbols               : ...
```

The counters classify `dhoro`, `satya`, and `mithya` as keywords; function definitions, returns, output, and library-function names under functions. Unknown symbols are printed but **not included** in the summary counts. The corrected lexer counts unterminated comments under `Symbols` to preserve the original project's counting convention.

## How the lexer works

```text
input.txt
    |
    v
Flex-generated scanner (lex.yy.c)
    |
    +--> Match reserved words, identifiers, literals, operators and symbols
    +--> Track line numbers and comments
    +--> Report unrecognized characters
    |
    v
output.txt
    +--> Token-by-token report
    +--> TOKEN SUMMARY
```

Flex chooses the **longest matching input**, so for example `>=` is recognized as one operator instead of `>` followed by `=`. For equal-length matches, earlier rules take precedence; the reserved-word rules occur before the general identifier rule.
